# АгроМаркет API — лабораторная работа №6

Express 5 + PostgreSQL 16: каталог с полным CRUD, заявки в базе, SQL-параметры, централизованные ошибки и Postman-коллекция. ФИО не указывается. Отчёт по предыдущей работе сохранён в [docs/LAB5.md](docs/LAB5.md) как история; текущее поведение описано здесь.

## Запуск на этом компьютере

В папке `agromarket-server`:

```sh
npm install
npm run db:local:start
npm run dev
```

База `agromarket` уже создана и заполнена четырьмя исходными товарами. Повторно выполнять `db:init` не нужно. Собственный кластер расположен в `.postgres/`; системные базы PostgreSQL не изменены. Он слушает только `127.0.0.1:5432`, использует пароль SCRAM, записанный в игнорируемый `.env`. Остановка: `npm run db:local:stop`. Это отдельный процесс, не служба автозапуска.

В соседнем `agromarket-react-main`: `npm install`, `npm run dev`. Сайт: `http://localhost:5173`, API: `http://localhost:3000/api`. В форме теперь можно выбрать товар.

## Запуск с собственной PostgreSQL

Нужны PostgreSQL 16 или 17 и Node.js 22.12+.

1. Создать пустую базу `agromarket`, например `createdb -U postgres agromarket`.
2. Скопировать `.env.example` в `.env`, указать свою строку подключения и пароль.
3. Выполнить `npm install`.
4. Выполнить `npm run db:init` один раз для пустой базы.
5. Выполнить `npm run dev` (наблюдение за файлами) или `npm start`.

`.env.example` содержит только образец. Не публикуйте `.env`, `.postgres/`, `node_modules/`. Спецсимволы пароля в URL нужно кодировать. CORS_ORIGIN должен совпадать с адресом frontend, включая порт.

Для новой локальной копии альтернативой шагам 1–2 служит `npm run db:local:start`: при отсутствии `.env` и `.postgres` он создаёт отдельный кластер, случайный пароль и базу. На macOS ищет Homebrew PostgreSQL 16, иначе использует PATH; путь к утилитам можно задать через `PG_BIN`.

**Сброс данных:** `npm run db:init -- --reset` удаляет все товары и заявки и заново переносит товары из JSON. Обычный `db:init` отказывается сбрасывать существующие таблицы. Создание схемы и перенос товаров выполняются в одной транзакции.

- `db/exercises.sql`, `db/exercises.js` — SQL-упражнения и воспроизводимые эксперименты.

## Эндпоинты

| Метод | Путь | Назначение | Ответы |
|---|---|---|---|
| GET | `/` | Текст о работе API | 200 |
| GET | `/api/health` | Сервер и соединение с БД | 200, 500 |
| GET | `/api/about` | Название, версия, author «Не указан» | 200 |
| GET | `/api/products` | Поиск, цена, сортировка, пагинация | 200, 400 |
| GET | `/api/products/:id` | Товар по ID | 200, 400, 404 |
| POST | `/api/products` | Создать товар | 201, 400 |
| PUT | `/api/products/:id` | Заменить товар | 200, 400, 404 |
| DELETE | `/api/products/:id` | Удалить товар, пустой ответ | 204, 400, 404 |
| GET | `/api/orders` | Заявки с product_name, фильтр status | 200, 400 |
| POST | `/api/orders` | Создать заявку | 201, 400 |
| PATCH | `/api/orders/:id` | Изменить status | 200, 400, 404 |

Неизвестный маршрут возвращает JSON 404. Непредвиденная ошибка любого SQL-маршрута — JSON 500 без внутренних подробностей.

Товар: обязательны непустая строка `name` и целое `price >= 0` в диапазоне PostgreSQL INTEGER. `category`, `image` по умолчанию NULL; `unit` — «кг». PUT заменяет все эти поля, а не только переданные.

Заявка: `name`, `email`, целое `quantity >= 10`; необязательные `product_id`, `phone`, `date`, `comment`. Поле формы `date` сохраняется в `delivery_date`, пустая строка превращается в NULL. Новая заявка получает `status: new`. `created_at` — время записи, `id` выдаёт база. Это отличается от названия `createdAt` в ЛР5; frontend это поле не использует.

PATCH принимает `{ "status": "processing" }`. Допустимы `new`, `processing`, `done`, `cancelled`; список проверяет CHECK базы. Переходы между этими значениями отдельно не ограничены.

## Бонусы

- Пагинация: `?limit=10&offset=20`; по умолчанию 20 и 0. Допустимый limit 1–100, offset — неотрицательное целое. Ответ остаётся массивом.
- Сортировка: `?sort=price`, `?sort=-price`, также `name` и `-name`. Столбцы только из белого списка; неизвестная сортировка возвращает порядок по id. При одинаковых значениях порядок стабилизирован по id.
- Фильтр заявок: `?status=new`; без параметра все заявки, новые сначала.
- Выбор товара: `<select name="product_id">` в React, либо общая заявка без товара. Каталог загружает все страницы по 100 товаров, поэтому список не обрезается первой страницей API.

Сохранён бонус ЛР5 `maxPrice`, совместимый с `search`, сортировкой и пагинацией. Пример: `/api/products?search=КЕК&maxPrice=1000&sort=price&limit=10&offset=0`.

## Проверки и Postman

```sh
npm test
npm run test:postman
npm run db:exercises
```

Нужна запущенная PostgreSQL и рабочий `.env`. Проверки создают собственные временные схемы `lab6_test_*` в этой базе, запускают API на свободных портах и удаляют схемы после завершения. Рабочие товары и заявки не сбрасываются. Пользователь БД для тестов должен иметь право CREATE SCHEMA.

`npm run test:postman` запускает коллекцию через Newman два раза на одной тестовой схеме. В каждом запуске 11 запросов, 20 assertions. В Postman Desktop: Import → выбрать JSON → Run collection. Переменная `baseUrl` уже задана как `http://localhost:3000/api`; `productId` и `orderId` сохраняются скриптами из ответов.

При запуске через Postman Desktop тестовый товар удаляется, заявка остаётся: DELETE заявки в ТЗ нет. Коллекция не зависит от прежних ID и проходит повторно. Команда `test:postman` дополнительно очищает всю собственную тестовую схему.

Newman нужен только для тестов (`devDependencies`), рабочий сервер его не использует. Аудит обнаруживает известные уязвимости транзитивных зависимостей Newman, совместимое автоматическое обновление их не устранило. Не запускайте непроверенные чужие коллекции. `npm audit --omit=dev` проверяет отдельно зависимости работающего API.

## Лабораторная 6 — SQL и ответы на эксперименты

Эксперименты выполнены на реальной PostgreSQL 16.13 в отдельной схеме. Небезопасный SQL не устанавливался в рабочий API.

Самый дорогой товар:

```sql
SELECT * FROM products ORDER BY price DESC, id LIMIT 1;
```

Результат исходного набора: «лол, 1 л», 4500 тг. Товаров дешевле 1000 три: 700, 600 и 350 тг. Категории в исходном JSON отсутствуют: одна группа NULL, count 4, округлённая средняя цена 1538. Поиск «мол» возвращает пустой массив, поскольку такого названия нет; «КЕК» находит товар без учёта регистра. Учебные INSERT/UPDATE/DELETE создали товар с ценой 100, изменили на 150 и удалили.

Реальные сообщения PostgreSQL:

| Эксперимент | SQLSTATE | Сообщение |
|---|---|---|
| Цена -5 | 23514 | `new row for relation "products" violates check constraint "products_price_check"` |
| Без name | 23502 | `null value in column "name" of relation "products" violates not-null constraint` |
| product_id 9999 | 23503 | `insert or update on table "orders" violates foreign key constraint "orders_product_id_fkey"` |
| quantity 5 без JS-проверки | 23514 | `new row for relation "orders" violates check constraint "orders_quantity_check"` |

Центральный errorHandler превращает эти ошибки в 400 с понятным `error` и техническим `detail`, как в ТЗ. `/api/products/abc` вызывает 22P02 → «Неверный формат значения». Дополнительно обработаны неверные даты и числа вне диапазона.

**SQL-инъекция.** При склеивании SQL строка `zzz' OR 1=1 --` вернула все 4 товара. Одна кавычка дала 42601 `unterminated quoted string at or near "' ORDER BY id"`; для необработанного маршрута это 500. С `$1` оба поиска возвращают пустой массив, а API отвечает 200: значения становятся данными, а не SQL-кодом. Все клиентские значения в рабочих запросах передаются параметрами. Только сортировка составляется из констант белого списка.

**Двойная защита quantity.** Обычный маршрут при 5 кг возвращает 400 «Минимальный объём заказа — 10 кг». В отдельном тестовом маршруте без этой JS-проверки CHECK базы отклоняет INSERT; errorHandler возвращает 400 «Значение не проходит проверку в БД». JS даёт понятное пользователю сообщение; CHECK гарантирует целостность даже при обращении к базе из другого скрипта.

**Связь заявки и товара.** Существующий product_id даёт product_name через LEFT JOIN. Несуществующий — 23503, обработчик возвращает 400 «Связанная запись не найдена». После удаления связанного товара заявка остаётся: product_id и product_name равны NULL благодаря ON DELETE SET NULL и LEFT JOIN.

**Статус.** PATCH с processing возвращает 200; lost нарушает CHECK и возвращает 400; отсутствующий status — 400; неизвестный ID заявки — 404.

**Использование ИИ.** Codex прочитал ТЗ, перенёс API на PostgreSQL, подготовил схему, скрипты, React-выбор товара, коллекцию, тесты и этот отчёт. Для защиты необходимо самостоятельно разобраться в коде.

## Вопросы для защиты

1. **Первичный и внешний ключ.** products.id и orders.id уникально определяют строки. orders.product_id ссылается на products.id. ON DELETE SET NULL сохраняет заявку при удалении товара, убирая связь.
2. **Ограничения orders.** PRIMARY KEY требует уникальный непустой id; NOT NULL — name, email, quantity, status, created_at; CHECK ограничивает quantity и status; REFERENCES требует существующий товар для ненулевого product_id. Нарушения дают соответственно 23505/23502, 23502, 23514 и 23503. DEFAULT задаёт new и текущее время, но сам по себе не является проверкой значения.
3. **SQL-инъекция.** Ввод становится исполняемой частью SQL при конкатенации. В routes/products.js поиск использует `ILIKE $1`, ID — `WHERE id=$1`; значения передаются отдельным массивом. Имя сортируемого столбца нельзя передать параметром, поэтому нужен белый список.
4. **.env.** Хранит пароль и настройки конкретного компьютера. Не попадает в Git. .env.example содержит только шаблон и нужен для настройки другого окружения.
5. **CRUD.** Create → INSERT → POST → 201; Read → SELECT → GET → 200; Update → UPDATE → PUT/PATCH → 200; Delete → DELETE → DELETE → 204. Неверные данные — 400, отсутствующая запись — 404.
6. **PUT и PATCH.** PUT заменяет поля товара целиком, необязательные пропущенные поля получают значения по умолчанию. PATCH изменяет только status заявки. DELETE 204 сообщает об успехе без тела, поэтому вызывается `.end()`.
7. **LEFT JOIN и JOIN.** LEFT JOIN сохраняет заявку без товара с NULL в product_name. INNER JOIN вернул бы только заявки с существующей связью.
8. **Ошибки Express.** Error middleware имеет четыре аргумента `(err, req, res, next)` и подключается после обычных маршрутов. Express 5 передаёт ему отклонённый промис async-обработчика. Текст неизвестной ошибки 500 и стек остаются только в терминале.
9. **JS и CHECK.** Проверка JS предназначена для понятной обратной связи, CHECK действует для всех способов записи в БД и защищает данные независимо от API.
10. **Пул и dotenv.** Пул переиспользует соединения вместо создания нового на каждый запрос. dotenv должен заполнить process.env до создания пула, иначе DATABASE_URL будет недоступен. Он импортирован первой строкой server.js и также в модуле пула для независимого запуска скриптов.
