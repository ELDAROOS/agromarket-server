# АгроМаркет API — лабораторная работа №5

ФИО не указывается по пожеланию пользователя. Поле `author` в `/api/about`: «Не указан».

## Запуск

Node.js 22.12+ (общая версия для frontend и backend). Два независимых проекта лежат рядом, у каждого свои зависимости и репозиторий:

```text
agromarket-react-main/
├── agromarket-react-main/  # React
└── agromarket-server/      # Express
```

В папке backend:

```sh
npm install
npm run dev
# http://localhost:3000, автоматический перезапуск при изменениях
# npm start — запуск без наблюдения
# npm test — проверки HTTP API и учебных экспериментов
```

Во втором терминале, в папке frontend: `npm install`, затем `npm run dev`. Открыть строго `http://localhost:5173`: этот origin разрешён в CORS. json-server больше не требуется. Если порт занят, остановите прежний сервер в его терминале.

## Структура

- `server.js` — запуск сервера, порт 3000 по умолчанию (`PORT` переопределяет).
- `app.js` — сборка Express-приложения, middleware, служебные маршруты, ошибки.
- `data/db.json` — копия товаров исходного проекта; названия сохранены.
- `data/products.js` — чтение JSON при старте относительно файла модуля.
- `routes/products.js` — список, поиск, фильтрация, сортировка, товар по ID.
- `routes/orders.js` — заявки в памяти, отдельное хранилище на экземпляр приложения.
- `middleware/logger.js` — метод, URL, итоговый статус и длительность запроса.
- `middleware/validateOrder.js` — проверка данных заявки перед созданием.
- `test/api.test.js` — интеграционные проверки на временных портах.

Логгер установлен перед `express.json()`, чтобы фиксировать также ошибки разбора JSON. CORS идёт первым, обработчик неизвестных маршрутов — после роутеров, обработчик ошибок — последним.

## Эндпоинты

| Метод | Путь | Описание | Ответы |
|---|---|---|---|
| GET | `/` | Текст «АгроМаркет API работает» | 200 |
| GET | `/api/health` | `status` и ISO-время `time` | 200 |
| GET | `/api/about` | `name`, `version`, `author` | 200 |
| GET | `/api/products` | Товары, `search`, `maxPrice`, `sort` | 200, 400 |
| GET | `/api/products/:id` | Один товар | 200, 404 |
| GET | `/api/orders` | Список заявок | 200 |
| POST | `/api/orders` | Создание заявки | 201, 400 |
| Любой | неизвестный адрес | JSON с полем `error` | 404 |

`search` ищет подстроку в названии без учёта регистра. `maxPrice` — включительная верхняя граница цены, неотрицательное конечное число. `sort=price` сортирует по возрастанию, `sort=-price` — по убыванию. Параметры работают вместе, исходный массив не меняется. Неверные параметры возвращают 400.

В исходных товарах нет молока или мёда: поиск `мол` возвращает `[]`; для непустого результата используйте `кек`. Примеры:

```text
http://localhost:3000/api/products/1
http://localhost:3000/api/products?search=КЕК&maxPrice=1000&sort=price
http://localhost:3000/api/products?sort=-price
```

## Заявка

```sh
curl -i http://localhost:3000/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"name":"Тест","email":"t@t.kz","phone":"+7 700 000 00 00","quantity":10,"date":"2026-10-20","comment":"Учебная заявка"}'
```

Обязательны непустые `name`, `email`, а также конечное числовое `quantity >= 10`. Дополнительные `phone`, `date`, `comment` — строки. Объём сохраняется числом, сервер добавляет `id` и `createdAt`. Успех: 201 и созданный объект. Ошибка: 400 и `{ "error": "..." }`. При `quantity: 5` текст: «Минимальный объём заказа — 10 кг». Некорректный JSON также даёт JSON-ответ 400.

Заявки хранятся только в памяти и исчезают при перезапуске, включая перезапуск `node --watch`. Это учебный API без авторизации, как требует лабораторная.

## Лабораторная 5 — ответы и эксперименты

1. `res.send('...')` для строки: `Content-Type: text/html; charset=utf-8`, статус 200. `res.json(...)`: `application/json; charset=utf-8`, статус 200. Для других типов аргумента `send` заголовок может отличаться.
2. До пользовательского 404 Express возвращает `/abc` как HTML с `Cannot GET /abc` и статусом 404. После добавления middleware: JSON `{ "error": "Маршрут GET /abc не найден" }`, статус 404.
3. `/api/products` и `/api/products/1`: 200; `/api/products/999`: 404.
4. Без `next()` и без отправки ответа цепочка останавливается, запрос остаётся ожидающим. В изолированном тесте ожидание прерывается через 150 мс; следующий маршрут не вызывается.
5. Логгер после маршрутов не видит запросы, на которые маршрут уже ответил без `next()`. Проверено на отдельном приложении; рабочий логгер установлен перед роутерами.
6. Без `express.json()` тело JSON не разбирается, `req.body` не заполнен; корректная по содержимому заявка получает 400 «Поля name, email и quantity обязательны». Проверено в изолированном приложении, разбор JSON в рабочем сервере включён.
7. CORS: `localhost:5173` и `localhost:3000` — разные источники из-за портов. Сервер может ответить 200, но без подходящего `Access-Control-Allow-Origin` браузер не разрешает JavaScript прочитать ответ. Настроен `http://localhost:5173`, включая preflight OPTIONS для JSON POST. CORS не заменяет авторизацию и не запрещает запросы через curl.
8. ИИ использован: Codex прочитал ТЗ, реализовал backend и бонусы, дополнил React, подготовил документацию и автоматические проверки. Перед защитой необходимо самостоятельно разобраться в коде.

## Вопросы для защиты

1. **Express и json-server:** json-server автоматически строит типовой API из JSON. В Express сами задаём маршруты, проверки, форматы ответов и middleware.
2. **req и res:** `req` описывает запрос (`req.params`, `req.query`, `req.body`), `res` формирует ответ (`res.status()`, `res.json()`, `res.send()`).
3. **params и query:** `/api/products/2` даёт `req.params.id === '2'`; `/api/products?search=кек` даёт `req.query.search === 'кек'`.
4. **Middleware:** функция `(req, res, next)` в цепочке обработки. Она отвечает сама или передаёт управление через `next()`. Без обоих действий запрос зависает.
5. **Порядок:** middleware выполняются в порядке подключения. Парсер должен работать до чтения тела, логгер — до отвечающих маршрутов; обычный 404 — после всех маршрутов, иначе он перехватит существующие адреса.
6. **CORS:** источник состоит из протокола, домена и порта; разные порты означают разные источники. Нужен разрешающий заголовок сервера.
7. **Серверная валидация:** HTML-атрибуты можно удалить или отправить запрос напрямую. Браузерная проверка помогает пользователю, серверная проверяет входящие данные независимо от клиента.
8. **Статусы:** 200 — успешный GET `/api/products`; 201 — созданная POST `/api/orders`; 400 — неверная заявка, например 5 кг; 404 — отсутствующий товар `/api/products/999` или маршрут `/abc`.
